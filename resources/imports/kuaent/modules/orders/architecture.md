# Orders — architecture

## Aggregate

An order is a snapshot of checkout (or sales-specialist placement):

```
Order
  ├── OrderItem[]          (sale | rental lines; bundle composition in meta)
  ├── OrderAddress[]      (type: billing | shipping; JSON `data`)
  ├── OrderPayment[]      (positive inflow + negative credit-note rows)
  ├── OrderShipment[]     (0..n; checkout creates one pending row)
  │     └── OrderShipmentAssignment?  (0..1; unique per shipment)
  ├── CreditNote[]        (issued refunds)
  │     └── CreditNoteItem[]
  └── RentalReservation[]  (rental module; confirmed at place)
```

`Cart.order_id` / `ordered_at` link the originating cart after place ([cart-checkout](../cart-checkout/)).

## Who writes the order

```
                    ┌─────────────────────────────────────┐
                    │           Order row                 │
                    └─────────────────────────────────────┘
         create ↑                         mutate ↑
                │                                 │
  Checkout OrderService::place()     Admin OrderController
  SalesSpecialistOrderService          OrderShipmentAssignmentService
    → OrderService::place()           CreditNoteService::issue()
  Finalize* jobs (payments)         InvoiceService (PDF file only)
    → OrderService::place()         OrderExportService::send()
    → status/payment sync            (external-catalog)
```

This module’s HTTP layer never calls `OrderService::place()`. Admin ops start from an existing `Order`.

## Admin vs customer vs specialist

| Surface | Auth | Scope |
|---|---|---|
| `/admin/orders/*` | `role:Admin` + `order_view` / `order_edit` | All orders |
| `/admin/assignments/*` | `role:Admin` + `assignment_*` | All assignments |
| `/api/v1/me/orders*` | Sanctum + `verified.if-required` | `orders.user_id = auth id` |
| `/sales-specialist/orders*` | `role:Sales Specialist` | `sales_specialist_id = auth id` — **not this module** |

Guest orders (`user_id` null) appear in admin. They do **not** appear in `me/orders` (that query is `where('user_id', $userId)`).

## Status vs payment vs fulfillment

Three independent views, all derived on `Order`:

1. **Workflow status** — `orders.status` + `Order::TRANSITIONS` (see [models.md](models.md)).
2. **Payment state** — `paymentState()` from payment rows vs `grand_total` (`unpaid` / `partial` / `paid` / `refunded` / `overpaid`). Used on the admin list, not stored.
3. **Fulfillment state** — `fulfillmentState()` from shipment statuses. Used on the admin list, not stored.

Admin list filters `payment=` and `fulfillment=` query these derived states (see [controllers.md](controllers.md)).

## After-commit side effects

`OrderObserver` is registered in `EventServiceProvider::boot()`.

On **create** (after the place transaction commits):

1. `MailService::notifyAdminNewOrder()` (if `notifications.admin.notify_new_order`).
2. `MailService::sendOrderStatus()` (if the matching `notifications.order.*` toggle is on).
3. If external order mode is **auto**: `SubmitExternalOrderJob::dispatch($order->id)` on queue `config('external_catalog.order_queue')` (default `imports`).

On **status change**:

- `MailService::sendOrderStatus()`; if new status is `shipped`, latest shipment `tracking_number` is passed in.

Invoice PDFs are **not** generated by the observer. They are generated by admin invoice actions or by `MailService::sendPaymentConfirmation()` (payments finalize path when `payment_methods.send_invoice` is true).

## PDF invoices

`InvoiceService` renders `resources/views/invoices/invoice.blade.php` via `Barryvdh\DomPDF\Facade\Pdf`, A4 portrait, and writes the **local** disk:

`invoices/INV-{order.number}.pdf`

Laravel’s `local` disk root is `storage/app/private` (`config/filesystems.php`). Download/preview read that file; missing files are generated on demand.

## Assignment vs shipment

Checkout creates an `order_shipments` row (customer-selected carrier snapshot). Admin may add more shipments.

An **assignment** is a separate row: staff pick a `shipping_methods` record (often a fulfillment provider) and a status/tracking. `OrderShipmentAssignmentService::syncToShipment()` copies status/tracking onto the shipment, may auto-transition the order to `shipped` / `completed`, then optionally calls `ShippingDriver::submitAssignment()` if the driver implements it (today: `BekiPostApiDriver`).

## External catalog

Setting key `product.external_order.mode` (`auto` | `manual`, default manual) via `ExternalCatalogOrderSettings`.

- **auto:** observer dispatches `SubmitExternalOrderJob`; admin “send” button is rejected.
- **manual:** admin `POST .../send-external` calls `OrderExportService::send()` directly.

Job class and exporter live in [external-catalog](../external-catalog/). This module only dispatches / invokes them.

## Request flow (admin show)

```
GET /admin/orders/{order}
  → order_view
  → load user, specialist, items, addresses, payments,
    shipments.shippingMethod, shipments.assignment.shippingMethod,
    rentalReservations.product.translations, creditNotes.items
  → PaymentMethod::forCurrentChannel()
  → ShippingMethod::active()->forCurrentChannel()
  → ExternalCatalogOrderSettings::isManual()
  → view admin.orders.show
```
